## 1. 背景

### 1.1 现状：界面自己就是管理员，而且没有后台

| 现状 | 问题 | 本文的处理 |
| --- | --- | --- |
| `Performix.App` 的 `app.manifest` 是 `requireAdministrator` | 整个 UI 进程（含 XAML 渲染、托盘、热键、通知）都跑在高完整性；UIPI、托盘、自启、通知的坑一个不少 | 界面降为 `asInvoker`，见 §4.3 权限墙 |
| 硬件写入发生在 UI 进程里 | 界面崩了硬件控制就断；换一个客户端（HUD/探针）就要再要一次管理员 | 宿主独占硬件（ADR-0001 D3/D4） |
| 没有任何常驻后台 | 开机后到第一次打开界面前，没有采样、没有失效保护、没有「归还风扇」 | 宿主改为自动启动的服务（D1/D2） |
| 旧版装过 WinRing0 驱动（`Overlay/WinRing0Cleanup.cs`） | 驱动路径的维护成本与被拦风险都被实测教育过 | 本文不引入任何驱动（C2/C8） |

### 1.2 为什么「宿主形态」必须现在定，而不是实现时再说

- ADR-0001 D3 只写了「单一特权宿主」，**没写它怎么活**：按需 UAC？计划任务？Windows 服务？
  三种都能实现管道服务端，但开机时机、崩溃恢复、Session 0 行为、账户权限完全不同。
- 界面一旦降权（D3 第 2 条），**所有持续性的提权动作**（硬件写入、后台采样、自动更新、第三方服务代办）
  都必须有人接住 → 宿主必须常驻，形态没有第二种选择的空间。
- 形态决定了协议层的细节：客户端能不能在登录前连上、重连策略、多会话谁是主控、服务升级窗口怎么兼容。
  这些返工一次的成本远高于现在把形态定死。

### 1.3 硬约束（本文的决策不能违反）

| # | 约束 | 来源 |
| --- | --- | --- |
| N1 | 宿主启动阶段的只读探测：**只调 `DSTS`，不调 `DEVS` / `INIT`**；读取串行化、频率 ≥500ms 一次 | [ASUS-ATK-FAMILY §9.4](../design/ASUS-ATK-FAMILY.md) |
| N2 | 不装驱动、不做直接 EC 端口 I/O | ADR-0001 C2 / C8 |
| N3 | 宿主协议不暴露任意命令面（无任意服务名 / 寄存器地址 / 路径） | ADR-0001 C9 |
| N4 | UI 不直接 P/Invoke 硬件，硬件访问只经宿主协议 | ADR-0001 C4 |
| N5 | fail-closed：未验证的能力只显示不写 | ADR-0001 D6 |
| N6 | 失败可回滚，不「写后不管」 | ADR-0001 C3 |
| N7 | 快速启动=休眠：服务不会重启，恢复后必须重新初始化 | 本文 D2 |

### 1.4 术语边界（避免和 ADR-0001 混用）

| 术语 | 含义 |
| --- | --- |
| **宿主** | `Performix.Host`，本机 Windows 服务进程（Session 0）；唯一的特权面 |
| **界面** | `Performix.App` + `Performix.Overlay`，普通用户权限；**客户端**指其中的宿主协议客户端 |
| **辅助进程** | 由宿主用 `WTSQueryUserToken` 在用户会话拉起的**受限、非提权**进程（D3 的逃生口），不是第二个宿主 |
| **安装程序** | 只在安装/升级/卸载时以管理员运行的一次性提权程序；所有一次性提权动作归它 |

## 2. 决策总览

一句话：**宿主是自动启动、最小权限的 Windows 服务，界面全程非提权；两者只通过一条显式 DACL、
命令白名单、带版本协商与心跳的本地命名管道通信；硬件写入与所有持续性提权动作由服务按白名单代办。**

```
 ┌── 用户会话（普通用户）──────────────┐        ┌── Session 0（Windows 服务）──────┐
 │ Performix.App / Performix.Overlay   │        │ Performix.Host                  │
 │  · UI / 托盘 / 热键 / OSD / toast    │◄──────►│  · 管道服务端（显式 DACL）        │
 │  · 管道客户端：Hello/心跳/退避重连   │ 本地管道│  · 命令白名单 + 参数范围校验      │
 │  · 只发意图；不碰 WMI / EC / 注册表  │        │  · IHardwareArbiter（ADR-0001 D4）│
 │  · 界面偏好写 HKCU / LocalAppData    │        │  · provider / 探测 / 审计日志     │
 └─────────────────────────────────────┘        │  · 电源 / 会话事件、失效保护      │
                                                │  · 后台任务：更新下载、服务代办    │
                                                └──────────────┬───────────────────┘
                                                               │ ACPI-WMI / ATKACPI / NVAPI
                                                               ▼
                                                             硬件 / EC
   ┌── 安装程序（一次性提权，只在装 / 升 / 卸时跑）────────────────────────────┐
   │ 自建 %ProgramData% 目录 + 显式 ACL（关继承、校验所有者）、注册服务与事件日志源、 │
   │ 写 HKLM 自启、授服务 INTERACTIVE 启动权、迁移旧配置、删除旧版提权任务         │
   └──────────────────────────────────────────────────────────────────────────┘
```

- **唯一常驻特权进程**：宿主。它自己就是最值得攻击的目标 → 安全责任在 D4。
- **界面只有一个通讯面**：管道。不是注册表、不是共享内存、不是窗口消息。
- **一次性提权只出现在安装程序**。

## 3. 决策

### D1 形态：自动启动的 Windows 服务（不用计划任务，也不用自启独立进程）

**决策**：宿主实现为 **`SERVICE_WIN32_OWN_PROCESS`** 的 Win32 服务，启动类型 **`Automatic`**。

| 维度 | Windows 服务（选用） | 计划任务（AtStartup） | 自启独立进程（Run / 启动文件夹） |
| --- | --- | --- | --- |
| 开机即用 | ✅ 服务控制管理器（SCM）在**登录前**拉起，不需要用户登录 | ⚠️ 能配成登录前，但要用 SYSTEM/服务账户；交互式任务要等登录 | ❌ 只能等用户登录，登录前没有后台 |
| 拿到 SYSTEM 级能力 | ✅ 账户由 `obj=` 指定（最小权限可用 `LocalService` + 服务 SID） | ⚠️ 只能靠「以最高权限运行」+ 特定账户，且不是服务令牌，行为与权限都不同 | ❌ 只有用户令牌 |
| 崩溃自恢复 | ✅ SCM Recovery：指定动作 + 重启间隔 + 失败计数重置 | ⚠️ 进程崩了任务算「已启动成功」，**不会重启**；挂死更检测不到，要自己造重复触发/看门狗 | ❌ 要自己写守护进程 |
| 弹窗 / 抢焦点 | ✅ Session 0，没有交互桌面 | ⚠️ 取决于账户与「交互」设置，可能弹 | ❌ 会弹、会抢焦点 |
| 单实例 | ✅ SCM 保证同一服务只有一个运行实例 | ⚠️ 多用户/多触发器下会有重叠实例 | ❌ 每个用户一份 |
| 状态可见性 | ✅ `sc query` / 服务管理器，状态机明确（STOPPED／RUNNING／PAUSED） | ⚠️ 任务状态与进程状态不一致 | ❌ 只能看进程 |

**为什么计划任务的坑不能接受**：

1. **电池策略默认就错**：任务计划程序默认「使用电池时不启动」（`DisallowStartIfOnBatteries`）
   和「电池模式时停止」（`StopIfGoingOnBatteries`）。笔记本拔掉电源后台就停 —— 而这正是最需要
   降功耗/看温度的时候。
2. **执行时限默认 3 天**（`ExecutionTimeLimit`）：长驻任务到点被终止；忘了改就是「三天后后台消失」。
3. **崩溃 ≠ 任务失败**：任务只要「成功启动进程」就算成功，进程之后崩了任务计划程序不管；
   要恢复就得配重复触发 + 自定义条件，等于在任务计划程序里重写一个更差的 SCM。
4. 交互式任务的账户/登录依赖让「登录前可用」和「能访问用户桌面」变成互斥选项。

**为什么自启独立进程不够**：只能在登录后启动、只有用户令牌、每个用户一份、崩溃恢复要自己写守护；
而且它要提权就绕不开 UAC 或计划任务 —— 等于曲线回到被否掉的两种方案。

> 结论：服务不是「更重的方案」，而是**唯一同时给到「登录前启动 + 可靠崩溃恢复 + Session 0 无界面」**的方案。
> 代价是安装/调试复杂度（§4.2），这个代价由安装程序与 §6 的落地步骤吃掉。

### D2 服务配置

**决策**：服务配置按下面这张表固化，安装脚本可重复执行（幂等），升级时只改差异。

| 项 | 值 | 为什么 |
| --- | --- | --- |
| 启动类型 | `Automatic`（`sc config … start= auto`） | 开机即用是选服务的第一理由。**不要**默认用 Delayed-Auto：界面刚登录就查状态会有一段时间连不上（客户端有退避，但没必要人为制造） |
| Recovery 动作 | 第一次 **1 s**、第二次 **5 s**、后续 **60 s** 重启 | 1 s 抓瞬时崩溃；60 s 兜长期故障（避免崩溃风暴打满 CPU / 日志） |
| Recovery 失败计数重置 | **1 天**（`reset= 86400`） | 偶发一次崩溃不应该让后续重启间隔永久停在 60 s |
| Recovery 触发面 | 开 `FailureActionsOnNonCrashFailures`（`sc failureflag … 1`） | 否则「服务进程干净退出但服务没在跑」（配置错、依赖缺、许可证过期）不触发恢复 —— 这恰恰是最常见的故障形态 |
| 服务账户 | **能满足就用 `LocalService`** + **服务 SID**（`SERVICE_SID_TYPE_UNRESTRICTED`）+ 设备对象 ACL + `RequiredPrivileges`；确实需要才 `LocalSystem` | 最小权限。管道 DACL、目录 ACL、设备句柄都能按服务 SID 精确授权，不需要系统级令牌 |
| `RequiredPrivileges` | 只保留实际用到的（起步 `SeChangeNotifyPrivilege`；电源相关按实测再加） | 默认账户带一堆用不到的特权，服务被拿下时特权越少损失越小 |
| `ImagePath` | **必须加引号**：`"C:\Program Files\Performix\Performix.Host.exe"` | 路径含空格时无引号 = unquoted service path 本地提权（攻击者在同目录放同名 exe 即可随服务启动执行） |
| 启动完成时机 | **尽快 `SERVICE_RUNNING`**，硬件初始化/探测放后台 | SCM 默认 **30 s** 超时，超时返回 1053（服务未及时响应启动请求）；ASUS/EC 初始化可能很慢，不能卡在启动路径里 |
| 接受的控制事件 | `STOP` / `SHUTDOWN` / `PRESHUTDOWN`（必须 `SERVICE_ACCEPT_PRESHUTDOWN` 显式声明）/ `POWEREVENT` / `SESSIONCHANGE` | STOP/SHUTDOWN 要归还风扇（ADR-0001 D5.1）；POWEREVENT/SESSIONCHANGE 见下表 |
| 服务依赖 | 不声明依赖 OEM 服务；诊断需要时只读检查其状态 | 声明依赖会让我们的服务被 OEM 服务的启停拖死（ADR-0001 D11 的教训） |
| 描述 / 显示名 | 固定（`Performix Host`），安装时写入 | 服务页与故障排查要用 |
| 日志归属 | 服务日志写 `%ProgramData%\Performix\logs`（服务自己写） | 界面无写权限，见 §4.3 |

**电源与会话事件（必须处理，不能只在退出路径上做失效保护）**：

| 事件 | 场景 | 服务要做什么 |
| --- | --- | --- |
| `PBT_APMSUSPEND` | 睡眠 / 休眠前 | 归还风扇固件控制、落盘状态、停止轮询（ADR-0001 D5.1） |
| `PBT_APMRESUMEAUTOMATIC` / `PBT_APMRESUMESUSPEND` | 唤醒 | **重新初始化硬件**（EC 可能复位）、重读运行时状态、重新应用用户模式与风扇策略；失败上报界面 |
| `WTS_SESSION_LOGON` / `LOGOFF` | 用户登录 / 注销 | 更新可连客户端与会话租约（D8）；注销时回收租约 |
| `WTS_SESSION_LOCK` / `UNLOCK` / `CONSOLE_CONNECT` / `DISCONNECT` | 锁屏 / 切换 / 接上或断开控制台 | 只读客户端不受影响；写租约按 D8 规则转移或冻结 |

**快速启动（Fast Startup / hybrid shutdown）的硬要求（N7）**：

- 关机时 Windows 会「休眠内核与会话」而不是完整关机 → **服务不走 SHUTDOWN 停止流程，下次开机也不是
  重新启动服务**，同一个进程上下文接着跑；但 EC / GPU / 固件已经复位过。
- 所以：**不能依赖「开机必有一次服务启动」来触发初始化**。初始化必须由「首次请求 / 会话登录 /
  电源恢复事件」任一触发，并且**幂等**（重复调用结果一致）。
- 「我一直在跑，所以状态还在」是本文明确禁止的假设。

### D3 Session 0 风险：服务没有桌面

**决策**：依附用户会话的能力**逐项验证**，验证不过就走 `WTSQueryUserToken` 辅助进程；
**不在服务里「硬做」**。

| 能力 | 在服务里的风险 | 判定方式 | 退路 |
| --- | --- | --- | --- |
| 显示器 DDC/CI（亮度、输入源、部分面板控制） | 服务没有交互桌面，`EnumDisplayMonitors` / SetupAPI 拿到的显示器句柄可能缺失、或指到别的设备；多显示器顺序不可靠 | 真机上「用户会话读值」与「服务读值」逐字段对照 | 辅助进程做，服务只转发 |
| 按会话的 GPU / 显示设置（HDR、色彩、独显直连后的显示状态、每应用 profile） | 与登录会话强绑定；服务里可能只读到「默认/全局」值 | 同一时刻两边各读一遍对照 | 辅助进程 |
| 音频端点 / 音量 / 默认设备 | 每会话概念；服务里没有目标会话的 endpoint | 只读对照 | 辅助进程 |
| 用户注册表（`HKCU`） | 服务拿不到「当前用户」的 HKCU（`LocalService` 下 HKCU 不是用户配置单元） | — | 界面自己读写，或辅助进程 |
| 窗口 / 托盘 / 通知 | 服务根本不该做（Session 0 不可见） | — | 界面做（§4.3） |

**辅助进程的四条要求**：

1. **按需拉起，不常驻**（登录时/有请求时），用完退出；
2. `WTSQueryUserToken(WTSGetActiveConsoleSessionId())` → `DuplicateTokenEx` → `CreateProcessAsUser`，
   以**用户令牌、非提权**运行；
3. 只做会话相关操作，经宿主协议的受控扩展回报；**不给它硬件写权限**；
4. 它崩溃不影响服务、不影响硬件状态。

**为什么验证标准必须是「读值逐字段相同」**：Session 0 里拿不到桌面的 API **往往不报错**，
而是返回一个看起来合理的默认值。写设置类操作会把默认值写回去 → 用户的设置被静默重置。
这是最隐蔽的一类 bug，所以判定标准不是「没报错」，是**两边数值一致**。

### D4 管道安全（排在消息格式之前）

**决策**：管道是**新增的本地权限边界**（任何本地交互用户都能尝试连接），先把它焊死，再谈消息长什么样。
顺序不能反：格式错了改协议，安全错了要发版。

| # | 威胁 | 措施 | 说明 |
| --- | --- | --- | --- |
| 1 | 本地任意用户连上管道发命令 | 服务端**显式 DACL**（不用默认 DACL）：`SYSTEM` / `Administrators` 完全控制；`INTERACTIVE` **只读写**（`FILE_GENERIC_READ` + `FILE_GENERIC_WRITE`），**不给 `FILE_CREATE_PIPE_INSTANCE`** | 给实例创建权 = 允许任何交互用户往同名管道加实例（混淆/钓鱼；客户端连到的可能是别人的实例） |
| 2 | 远程 / 网络访问 | 创建时带 **`PIPE_REJECT_REMOTE_CLIENTS`** | 本地 IPC 没有理由接受经 SMB 的远程命名管道连接 |
| 3 | 服务未启动时管道名被抢注 | 服务端创建首实例带 **`FILE_FLAG_FIRST_PIPE_INSTANCE`** | 别人先建同名管道 = 假服务端；带这个标志后 CreateNamedPipe 会失败并给出明确错误，而不是复用别人的实例 |
| 4 | 客户端连到假服务端 | 连上后 `GetNamedPipeServerProcessId` 与 **SCM 查到的服务 PID**（`QueryServiceStatusEx` → `SERVICE_STATUS_PROCESS.dwProcessId`）比对；不一致 → 断开 + 告警 | 只比进程名不够（同名可伪造），PID 来自 SCM 才是真值 |
| 5 | 客户端被服务端模拟（服务端借客户端令牌做别的事） | 客户端 `CreateFile` 打开管道时带 **`SECURITY_SQOS_PRESENT` + `SECURITY_IDENTIFICATION`** | 默认服务端可以 `ImpersonateNamedPipeClient`；identification 级别下服务端拿不到可用令牌 |
| 6 | 服务端被冒名调用者骗 | 服务端 `GetNamedPipeClientProcessId` + `ImpersonateNamedPipeClient`，至少确认**用户 SID / 会话 id / 进程映像路径与签名 / 完整性级别** | 校验失败按未授权处理（`denied` + 审计），不「先服务了再说」 |
| 7 | 协议退化成万能操作面板 | **命令白名单**：业务级命令 + 参数范围校验；**绝不提供「写任意寄存器 / 任意端口 / 执行任意路径」** | 与 ADR-0001 C9 一致；服务页的「停服务」参数是**已知服务 ID**，不是服务名字符串 |
| 8 | 本地 DoS | 实例数上限（D8：4）、单连接并发/速率上限、半帧超时断开 | 别把管道当性能瓶颈，但它也是攻击面 |

- **服务启动时自检**：读回自己的服务 DACL 与管道 ACL，发现被改 → 记审计 + 拒绝启动（或降级为只读并显式上报）。
- **客户端连接前**先 `WaitNamedPipe` 带超时，拿不到按 D6 退避，不要 `CreateFile` 死循环。

### D5 消息格式

**决策**：**字节模式管道**（`PIPE_TYPE_BYTE` + `PIPE_READMODE_BYTE`），**4 字节长度头 + 负载**，
负载 UTF-8 JSON。

1. **帧**：`[u32 length][payload]`；`length` 是负载字节数，**不含 4 字节头**，小端。
2. **单帧上限 1 MB**：超过即回 `badRequest` 并断开（不读进内存），防止本地内存耗尽。
3. **信封**：`{ "v": 1, "id": "…", "type": "…", "payload": { … } }`
   - 请求 → 响应按 `id` 对应（客户端生成，同一连接内唯一；服务端原样回填）；
   - 服务端主动推送用独立 `type`（如 `event.modeChanged` / `event.progress`），`id` 可为空；
   - **未知字段忽略**（前向兼容）；**未知 `type` / 未知命令 → 回错误码、不断连接**
     （断连接会让客户端进重连风暴）。
4. **错误码**固定小集合：`ok` / `badRequest` / `unsupported` / `denied` / `busy` / `timeout` /
   `internal` / `incompatible`。错误只回「机器可读码 + 可翻译 key」，**不回堆栈、不回本机路径**。
5. 大对象（探测导出、日志导出）走**分块 + 每块 `id` 关联**，或「服务端写文件 + 回文件令牌」，
   **不要把几十 MB 塞进一条消息**。
6. 字段命名风格实现时二选一定死（`snake_case` 或 `camelCase`），写进协议文档；不要两种混用。

### D6 超时与重连

**决策**：客户端把「后台不在」当正常状态处理，**不弹框**；服务端把「客户端半死不活」当攻击面处理。

**客户端**：

| 情形 | 处理 |
| --- | --- |
| 连接时 `ERROR_FILE_NOT_FOUND`（管道不存在 = 服务没起/正在重启）或 `ERROR_PIPE_BUSY`（实例满/正忙） | 按 **0.5 s / 1 s / 2 s** 退避重试，总上限 **5 s**；界面显示「后台未连接」，需要后端的控件禁用 + 原因；**不弹框**、不弹气泡 |
| 单个请求 | **5 s** 超时；超时按 `timeout` 处理，**写命令不自动重发** |
| 慢操作（探测、应用模式、更新下载） | 服务端**立即受理**（回 `accepted` + 作业 id）→ 进度事件 → 完成/失败事件；客户端可按作业 id 取消 |
| 心跳 | **5–10 s** 一次 `ping`；**连续 2 次超时** → 判定连接死 → 主动断开重连 |
| 重连成功 | **重新拉全量状态**（服务端是唯一事实源）；**不补发**断线期间的写请求，改为读回来让用户确认 |

**为什么必须有应用层心跳**：服务端挂死 / 被调试器挂起 / 死锁时，管道可能没有 EOF，
客户端收不到 `ERROR_BROKEN_PIPE`，只看「请求超时」会一直等。心跳把「挂死」变成可判定的超时。

**服务端**：

| 情形 | 处理 |
| --- | --- |
| 半帧（长度头到了、负载没到） | 超时断开（防慢速连接占实例） |
| 连接断开 / 心跳超时 | 清理该连接的作业与租约 |
| I/O 模型 | **overlapped I/O**；每连接一个读取循环，不阻塞工作队列（D8 的串行化在队列里，不在 I/O 线程里） |
| 写回 | 单连接内响应串行写；推送事件与响应共用写锁，避免交错 |

**写操作必须幂等**：命令语义是「**设为 X**」而不是「**加 1**」「**切换一下**」。
理由：重连后客户端会重拉状态、用户可能重试；非幂等命令在重试下会叠加（「+1 档」连点两次 = 错档位）。
「切换」类命令一律拆成「读当前 + 设为目标」，或由服务端按目标值执行。

### D7 版本协商

**决策**：**管道名不带版本**（固定 `\\.\pipe\PerformixHost`）；版本在应用层协商。

1. **首帧必须是 `Hello`**：`Hello { protoMin, protoMax, appVersion, capabilities }`（客户端 → 服务端）。
2. 服务端在 `[protoMin, protoMax]` 内选自己支持的最高版本，回 `HelloAck { proto, serverVersion, serverCapabilities }`；
   无交集 → 回 `incompatible` 并**断开**；客户端显示「请更新应用/服务」并给出双方版本号。
3. **Hello 之前的任何其它命令一律拒绝**（含 `ping`）——防止老客户端按旧格式乱发被误解析。
4. **协议版本与产品版本解耦**：`appVersion` 只用于诊断与兼容提示，不能拿来推协议版本
   （内部版本号可以天天改，协议不必动）。
5. 服务端**至少支持 N 与 N-1**：升级窗口里「应用先更新」或「服务先更新」都不能把用户搞砖。
6. **`capabilities` 与版本分开**：同协议版本也可能能力不同（机型、配置、服务端开关）。
   能力协商结果进快照，界面按「没有这个能力」渲染，而不是「调用后报错」。

### D8 多实例、单写者与会话租约

**决策**：

1. **宿主单实例由 SCM 保证**；服务内部**单一工作队列串行**处理硬件操作（与 ADR-0001 D4 的
   `IHardwareArbiter` 对齐：所有客户端的请求进同一个串行队列，写租约在队列里判）。
2. **界面按会话单实例**：`Local\Performix.App.SingleInstance` 命名互斥体。
   用 `Local\` 而不是 `Global\`：`Local\` 是会话本地命名空间 → 每个登录会话一个界面实例，
   不会把另一个用户会话的窗口顶掉。第二实例唤起已有窗口后退出。
3. **多会话用「控制权租约」（control lease）**：
   - 同一时刻**只有一个客户端有写权限**；
   - 租约默认给**活动控制台会话**（`WTSGetActiveConsoleSessionId()`）；
   - 其余会话/客户端**只读**：可读快照、可订阅事件，写命令回 `denied` + 原因（「另一个会话正在控制」）；
   - 租约随会话切换 / 注销回收：原主控断开 → 先冻结一小段时间 → 新活动控制台会话可接管；
     原主控回来只能只读，直到再次成为活动控制台或按策略显式请求；
   - 租约状态进快照（谁持有、何时获取、是否只读），界面要能解释「为什么我这台不能改」。
4. **管道实例数上限 4**（不用 `PIPE_UNLIMITED_INSTANCES`）：App / Overlay / 诊断工具 / 辅助进程
   四个足够；第 5 个连接按 `ERROR_PIPE_BUSY` 回退重试。避免本地进程开几百个连接拖死服务。
5. 服务端维护连接表：连接 → 会话 id、用户 SID、进程 id、是否持有租约、最后心跳时间；
   诊断快照可见（ADR-0001 D4.8 的可观测性要求）。

## 4. 后果

### 4.1 正面

- 界面可以全程 `asInvoker`：**UAC 只在安装/升级时出现一次**；
- 开机即用、崩溃自恢复由 SCM 提供，不需要自己写看门狗；
- 服务在 Session 0 → 不弹窗、不抢焦点；托盘/通知留在用户会话由界面做；
- 单一特权面 + 命令白名单 + 显式 DACL，攻击面比「UI 自己提权 + 到处 P/Invoke」小得多；
- 协议与产品版本解耦，应用/服务可以分别升级。

### 4.2 负面 / 成本

- **安装/卸载复杂度上升**：注册服务、建目录 ACL、注册事件日志源、授服务 DACL、迁移旧数据、
  清理旧提权任务，全都要可重复执行（§4.3 / §6）；
- **调试变难**：服务在 Session 0，断点、日志、崩溃转储都要专门配置；不能「F5 起服务」；
  开发期要有一条「控制台宿主」的调试路径；
- **Session 0 依附能力要逐项验证**，可能有一块功能只能走辅助进程（多一种进程形态要维护）；
- **服务自己成了最有价值的攻击目标**：管道安全（D4）、命令白名单、自动更新的签名校验都要加；
- **多会话租约带来新的 UI 状态**（「另一个会话正在控制」），需要文案与诊断支持；
- **快速启动/睡眠恢复**必须专门测，否则会出现「服务还在跑但硬件状态早没了」的静默错误（N7）。

### 4.3 界面降为非提权后的权限墙

> 界面改成 `asInvoker` 之后，原来「管理员 UI 顺手就做了」的事全部变成权限问题。
> 这张表是**逐项裁决**：每一行都必须有确定解法，不允许「先试试，不行再说」。
> 列读法：**会遇到什么** = 不提权时的真实报错/现象；**风险** = 这个解法本身引入的风险。

| 操作 | 会遇到什么 | 解法 | 风险 |
| --- | --- | --- | --- |
| 写 `%ProgramData%` 配置与日志 | 安装程序建的 `%ProgramData%\Performix` 默认 Users 不可写 → 写配置/日志直接 `Access Denied`；若图省事给 Users 写权限，等于把**服务会读的配置**开放给任意本地用户 | **按归属拆开**：影响服务的配置由**服务**写，界面通过管道请求；界面偏好放 `HKCU` / `%LocalAppData%`；界面日志写 `%LocalAppData%\Performix\Logs`，服务日志留 `%ProgramData%\Performix\logs`。**绝不给 Users 开放服务配置目录的修改权限**（等于提权）；安装程序**自建**目录并设显式 ACL（关继承、校验所有者）防预建；旧文件迁移在安装时以管理员完成 | 权限一松就是本地提权（改配置 → 服务按恶意配置加载/执行）；「界面和服务各写一半」会分裂事实源；迁移写错会丢用户旧设置 |
| 注册开机自启 | 写 `HKLM\...\Run` 需要管理员；旧版留下的提权启动项/计划任务还在，会和新服务并存 | 服务已自动启动 → **界面不需要系统级自启**；界面要「开机自启」就写 `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`（无需提权）；对所有用户生效由**安装程序**写一次 `HKLM\...\Run`；**尊重任务管理器的禁用状态**（`StartupApproved\Run` 的启用位）；旧版提权任务必须由安装程序删除，否则并存 | 只写 HKCU = 每用户一份，换用户就没了；无视 `StartupApproved` 会造成「用户关了又自己起来」；旧任务不删 → 两个宿主抢硬件（最严重，见 ADR-0001 D11 竞争检测） |
| 控制系统服务 | 非管理员 `StartService` / `ControlService` → `ERROR_ACCESS_DENIED`（SCM 对象默认只给管理员）；服务被停/崩之后，普通权限的界面自己拉不起来 | 安装时给**自家服务** DACL 授 `INTERACTIVE` **启动权**（必要时停止权）→ 服务挂了界面能拉起；**第三方服务只能由后台按白名单代办**（命令参数是「已知服务 ID」不是服务名字符串）；**不能提供「控制任意服务」的通用命令** | 授权只到 `SERVICE_START`（必要时 `SERVICE_STOP`）；给到 `SERVICE_CHANGE_CONFIG` / `WRITE_DAC` 就过分了；白名单外的服务一律拒绝，否则管道变成任意服务控制器（C9） |
| UIPI（用户界面特权隔离） | 中完整性进程向高完整性窗口 `SendMessage` / `PostMessage` 会被**静默丢弃**（返回值像成功了）；`SendInput`、低级键盘钩子也作用不到提权窗口；过渡期旧版提权界面的单实例唤醒消息会被拦掉 | 界面与服务**只走管道**；全局热键改用 **`RegisterHotKey`**（系统投递，不受 UIPI 限制）而不是低级键盘钩子；确需操作提权窗口才 `uiAccess=true`（**要签名并装进 `Program Files`**）；过渡期由**安装程序先结束旧进程**；**不要随手 `ChangeWindowMessageFilterEx`** | `ChangeWindowMessageFilterEx` 放宽的是全局消息过滤 → 等于自己拆掉一部分 UIPI；`uiAccess` 需要受信任位置 + 签名，发布/维护成本高，别为「顺手」加 |
| 托盘 | 提权进程**默认收不到 `TaskbarCreated`**（Explorer 重启后托盘图标不回来）；服务在 Session 0**不能弹通知** | 托盘放**界面**（普通权限反而少坑，提权进程才是特例）；必须处理 **`TaskbarCreated`** 重新加图标；服务告警走管道推给界面，由界面弹 toast；**未打包应用**要用开始菜单快捷方式注册 **AUMID**，否则 toast 不显示 | 提权进程里 `Shell_NotifyIcon` 会「成功」但 Explorer 重启后图标消失（静默）；AUMID 注册错位置 toast 静默丢弃，用户收不到告警 |
| 窗口层级与焦点 | 普通进程不能调提权窗口的 Z 序；`SetForegroundWindow` 受**前台锁**限制（可能只闪任务栏）；服务没有桌面 | OSD/浮层用 **`WS_EX_NOACTIVATE` + `SW_SHOWNOACTIVATE` + `TOPMOST`**，显示但不激活；只在用户**点托盘**时 `SetForegroundWindow`；独占全屏游戏看不到置顶窗是**系统行为**，不要绕 | 硬抢焦点会被系统拒绝 + 体验差；`AttachThreadInput` 之类绕前台锁的 hack 不稳定，别用 |
| 其它同类（写 `HKLM`、打开设备句柄 `\\.\…`、部分 `powercfg`、防火墙规则、加载驱动） | 都需要管理员或驱动签名；事件日志源注册也要管理员 | **一次性**的交**安装程序**；**持续性**的交**服务**；事件日志源由安装程序注册；自动更新由**服务**下载并**校验签名**后安装，**不允许服务执行界面传来的任意安装包路径**（也不允许界面指定更新包路径） | 设备句柄在服务里拿到的对象可能和用户会话不同（Session 0，见 D3）；自动更新是最高危路径（「任意路径 + 高权限」= 任意代码执行），必须固定源 + 签名校验 + 不接受界面参数 |

**总原则（三句话，比上面每一行都重要）**：

1. **一次性提权放安装程序**（建目录/ACL、注册服务、事件日志源、HKLM 自启、删旧任务、迁移旧配置）。
2. **持续性提权由服务按白名单代办**（第三方服务控制、需要特权的写、自动更新安装）。
3. **界面只发意图**，并且**不能直接写服务会读取的任何数据**（配置、日志、白名单、更新包路径）——
   否则界面就成了服务输入侧的注入面，前面所有安全措施都白做。

### 4.5 不做的后果

- **不做服务、继续「UI 提权 + 每次 UAC」**：UIPI 反噬、开机无后台、崩溃即失去控制 →
  ADR-0001 D3 的「UI 降权」目标无法达成；
- **做了服务但不做管道安全**：本地提权洞（任意用户连接 / 假服务端 / 命令注入）——
  比不做更糟，因为我们亲手造了一个常驻特权进程；
- **做服务但 Session 0 不逐项验证**：用户设置被「默认值」静默重置（最隐蔽的一类 bug）；
- **只做计划任务**：笔记本电池策略 + 3 天执行时限 + 崩溃不重启 → 后台随时消失，用户以为「工具坏了」。

---

## 5. 备选方案

| 方案 | 结论 | 原因 |
| --- | --- | --- |
| 计划任务（AtStartup，SYSTEM） | ❌ 不采用 | 电池默认策略、执行时限默认 3 天、崩溃/挂死不触发恢复、任务状态与进程状态不一致（D1） |
| 自启独立进程（`Run` / 启动文件夹） | ❌ 不采用 | 登录后才起、用户令牌、每用户一份、崩溃恢复要自己写守护（D1） |
| 每次按需 UAC 提权（ADR-0001 D3 原方案） | ⚠️ 仅保留为**排障/一次性工具** | 每次弹 UAC、无法后台、用户点「否」就全不可用；作为「安装程序」和「诊断工具」的一种形态保留，不做常驻 |
| 内核驱动 / 常驻过滤驱动 | ❌ 红线 | 不装驱动是 C2/C8；驱动战场与杀软/反作弊冲突（WinRing0 的历史） |
| COM 本地服务器（`LocalServer32`）/ 自建 RPC | ❌ 不采用 | 相比命名管道没有收益；DCOM 的权限模型更绕、攻击面更大；跨会话行为更难验证 |
| MSIX 打包 + 后台任务 | ❌ 不采用（当前） | 后台任务能力受限、依赖包身份与签名链；当前发布形态是未打包应用（托盘/toast 已受影响） |
| 保留「提权 UI 单进程」，只在需要时起第二个提权 helper | ❌ 不采用 | 两个提权进程更容易抢硬件；UIPI/托盘/自启问题一个都不解决（等于本文 §1.1 的现状） |
| 服务 + 计划任务混合（服务主控，任务兜底） | ❌ 不采用 | 两套自启/守护机制互相打架（重复实例、恢复动作竞争），排查成本翻倍 |

## 6. 落地顺序

> 原则：**先协议、再安全、再功能、最后降权**。步骤 0–2 可以在界面仍是提权 UI 的情况下完成
> （只是把通讯换成管道），这样能逐步替换而不断档。

| 步骤 | 内容 | 退出条件（可验收） |
| --- | --- | --- |
| **0** 协议骨架 | 定义帧 / 信封 / `Hello` / 错误码 / 命令白名单草案；用「控制台宿主」跑通本地回环（不做服务、不降权） | 帧解析、超界帧、未知命令、版本无交集四类用例全过 |
| **1** 服务骨架 | 安装/卸载脚本（`sc create` + Recovery + 服务 SID + SDDL）；尽快 `SERVICE_RUNNING`；`POWEREVENT` / `SESSIONCHANGE` 处理；快速启动恢复幂等 | 重启 / 睡眠 / 快速启动三条路径的日志能证明「重新初始化」真的发生（N7） |
| **2** 管道安全 | D4 全部措施：显式 DACL、`FILE_FLAG_FIRST_PIPE_INSTANCE`、`PIPE_REJECT_REMOTE_CLIENTS`、PID 比对、`SECURITY_IDENTIFICATION`、impersonation 识别、实例上限 | 假服务端 / 非管理员连接 / 越权命令 / 伪造 PID 四个安全用例**全部在服务端被拒并进审计** |
| **3** 只读命令 + 连接管理 | `GetSnapshot`、心跳、退避重连、全量重拉；界面显示「后台未连接」（不弹框） | 杀服务 / 挂死服务 / 重启服务三种故障下界面表现符合 D6，无弹框、无重连风暴 |
| **4** 写命令 + 仲裁 | 白名单命令 + 参数范围 + 幂等语义 + 会话租约；接 ADR-0001 D4 的 `IHardwareArbiter` | 两客户端并发写测试通过；断线重连后状态一致（重拉全量） |
| **5** 界面降权 | `app.manifest` → `asInvoker`；逐项验证 Session 0 能力（D3），不行就上辅助进程；托盘/热键/OSD 迁移完成 | **普通用户**完整跑通「看状态 → 切模式 → 看 OSD」，全程无 UAC 弹窗 |
| **6** 安装程序 + 收尾 | 目录 ACL（关继承 / 校验所有者 / 防预建）、服务 DACL、事件日志源、HKLM 自启、删旧提权任务、旧配置迁移、文档同步 | 全新机器安装 → 普通用户 → 全部功能可用；卸载干净（服务 / 目录 / 日志源 / 计划任务 / 注册表项） |

## 附录 B：服务安装配置清单（示意，未执行）

> 这些是**形状**，不是可直接粘贴的最终脚本；实现时以安装程序代码 + 实测复核为准。
> 关键点：所有命令都要**幂等**（重复执行结果一致），升级只改差异。

```bat
:: 注册服务：自动启动 + LocalService + 带引号的 ImagePath + 显示名
sc create PerformixHost binPath= "\"C:\Program Files\Performix\Performix.Host.exe\"" ^
   start= auto obj= "NT AUTHORITY\LocalService" DisplayName= "Performix Host"

:: 服务 SID（用于按 SID 授管道 ACL / 目录 ACL / 设备对象 ACL）
sc sidtype PerformixHost UNRESTRICTED

:: Recovery：1s / 5s / 60s，失败计数 1 天重置；非崩溃失败也触发恢复
sc failure PerformixHost reset= 86400 actions= restart/1000/restart/5000/restart/60000
sc failureflag PerformixHost 1

:: 最小特权（只留实际用到的）
sc privs PerformixHost SeChangeNotifyPrivilege

:: 服务 DACL：目标是「默认 DACL + 一条 INTERACTIVE 启动 ACE」
:: 做法：sc sdshow 拿到当前 SDDL → 在 DACL 里插入下面这条 ACE → 整体 sc sdset 写回
:: 只加不删；改完必须 sc sdshow 复核，并保留 SYSTEM / Administrators 完全控制
:: 要插入的 ACE 片段（不是可执行命令；等价「查询状态 + 启动」，必要时再加 WP 停止权）：
(A;;CCLCSWRP;;;IU)
```

**管道 ACL（代码里设，不是 `sc`）**，等价 SDDL 片段：

```text
D:(A;;FA;;;SY)(A;;FA;;;BA)(A;;GRGW;;;IU)
```

- `FA` = 完全控制（SYSTEM / Administrators）；`GRGW` = 读 + 写（INTERACTIVE）；
- **不给 `FILE_CREATE_PIPE_INSTANCE`**（不要写 `0x00000004` 那一类实例创建权）；
- 创建时带 `PIPE_REJECT_REMOTE_CLIENTS`，首实例带 `FILE_FLAG_FIRST_PIPE_INSTANCE`。

## 附录 C：术语

| 术语 | 含义 |
| --- | --- |
| 宿主 / Host | `Performix.Host`，本机 Windows 服务，唯一特权面 |
