## 1. 背景

### 1.1 现在只有「三态」，它回答不了用户的问题

ADR-0001 D6 解决的是**我们自己的纪律**：没验证过的能力不能自动写。但产品要回答的是**用户的五个疑问**：

| 用户会问 | 三态能不能答 | 差距 |
| --- | --- | --- |
| 这个功能我这台机器有没有？ | 部分（`Declared` 只说数据文件这么写） | 分不清「没有」和「还没查出来」 |
| 为什么这个开关是灰的？ | 不能 | 三态没有「原因」，`Unavailable` 粒度太粗 |
| 是我哪里没弄好，还是机器就这样？ | 不能 | 「缺驱动」「没授权」「管理员锁了」被压成同一个灰 |
| 现在到底能不能信这个数字？ | 不能 | 没有「读到了但可能是假值」这一档 |
| 我这台机器上这项是不是坏了？ | 不能 | 没有「写失败」这一档 |

### 1.2 三种失败模式（本文要防的事）

1. **读和写混判**：读到值就显示可用 → 用户点下去写失败；或者不能写就把读值一起藏掉 →
   本来能看的温度变成「不可用」。两者都是把「能读」和「能写」当成一个布尔。
2. **把「权限不足」写成「不支持」**：最贵的一类错——用户被明确告知「你的机型没有这个功能」，
   于是永远不再尝试、也不再报 bug；而真相可能是缺驱动、没提权、管理员策略，或调用进程的完整性级别不对。
   [ASUS-ATK-FAMILY §10](../design/ASUS-ATK-FAMILY.md) 的 `0x80041003` 就是活例：第一轮归因为
   「厂商 ACL」，第二轮证明是调用进程处于 Low IL。
3. **把「不确定」显示成「确定」**：0 个实例、假传感器值、共享缓冲残留都长得像真数据
   （[ASUS-ATK-FAMILY §9.5](../design/ASUS-ATK-FAMILY.md)）。

### 1.3 两份评审的分工

| 材料 | 视角 | 解决 | 本文落点 |
| --- | --- | --- | --- |
| A：九态「功能可用性」模型 | 产品 / UI | 用户看到什么、能点什么、文案怎么说 | §3（D1–D10） |
| B：令牌画像 / 错误分类 / 启动期探测 | 工程 | 状态凭什么判定、判定要什么证据、什么时候跑 | §4（D11–D21） |

两者不是并列的两套：**A 是出口，B 是入口**。B 探测出的证据必须能落到 A 的九态之一；
落不进去就说明证据不够（落 `检测中` / `未检测到`），**不许猜一个状态填上去**。

### 1.4 硬约束（本文的决策不能违反）

| # | 约束 | 来源 |
| --- | --- | --- |
| A1 | fail-closed：没验证过的能力不自动写 | ADR-0001 D6 / ADR-0002 N5 |
| A2 | 能力没声明 → 隐藏；声明了但当前不可用 → 禁用 + 原因，不许「灰着不解释」 | ADR-0001 C6 / D6 |
| A3 | 只读探测边界：只调 `DSTS`，不碰 `DEVS` / `INIT`；不改 ACL、不装驱动、不提权 | [ASUS-ATK-FAMILY](../design/ASUS-ATK-FAMILY.md) §9.4 / §9.8 |
| A4 | 每次写入记审计（含回读值）；失败可回滚，不「写后不管」 | ADR-0001 D5.3 / C3 |
| A5 | 不装驱动、不做直接 EC 端口 I/O | ADR-0001 C2 / C8 |
| A6 | 探测跑在宿主（ADR-0002 的 Windows 服务，`LocalService` 起步）；界面不碰 WMI | ADR-0001 C4 / ADR-0002 D1 / D2 |

## 2. 决策总览

一句话：**内部按「是否存在 / 能否访问 / 数据是否可信」三个维度判定，读和写分开算；对外只呈现九种状态
（可用 / 检测中 / 未检测到 / 不支持 / 需授权 / 策略锁定 / 只读 / 数据存疑 / 故障）；只有「可用」且
依赖输入全部可信才允许自动写；只有「故障」用红色；只有拿到确定证据才敢说「不支持」；证据来自令牌画像 +
分层错误码 + provider 元数据 + PnP 交叉验证；探测异步、single-flight、缓存键含令牌画像、只对瞬时错误重试。**

```
  ┌────────────────── 探测（材料 B）──────────────────┐
  │ 令牌画像 → 连接 → 类定义 → 实例枚举 → PnP 交叉验证  │
  │ 错误分层 + provider 元数据 + 事件日志（只导出）      │
  └────────────────────────┬──────────────────────────┘
                           │ 证据
                           ▼
  ┌──────────────── 内部三维（材料 A）────────────────┐
  │ 是否存在：有证据 / 无证据（不确定）/ 确认不存在      │
  │ 能否访问：可读写 / 需授权 / 策略禁止 / 被拒          │
  │ 数据可信：可信 / 未出结果 / 存疑 / 写后不一致        │
  └────────────────────────┬──────────────────────────┘
                           ▼ 合成（优先级 D4、证据门槛 D6）
  ┌──────────────── 对外九态（唯一口径）──────────────┐
  │ 可用 / 检测中 / 未检测到 / 不支持 / 需授权 /        │
  │ 策略锁定 / 只读 / 数据存疑 / 故障                   │
  └────────────────────────┬──────────────────────────┘
                           ▼
      UI（视觉纪律 D5 / 合并横幅 D7 / 诊断页 D9 / 文案 D10）
                           ▼
      自动写闸门（D3：状态=可用 且 全部依赖输入可信）
```

- **唯一出口**：九态。任何地方要把状态翻译成 UI 表现，都必须先落到九态。
- **唯一写闸门**：D3。九态里除「可用」以外**一律不自动写**。
- **唯一顺序**：多原因并存按 D4 取一个，主界面不并列显示两个结论。

## 3. 决策（产品口径：内部三维 → 对外九态）

### D1 读和写分开判；内部只保留三个维度

**决策**：能力状态不是一个枚举，而是**读侧 + 写侧**两个判定，各自取证后合成一个对外状态。
内部只保留三个维度：

| 维度 | 取值 | 证据来自 |
| --- | --- | --- |
| 是否存在 | 确认存在 / 无证据（不能确定没有）/ 有证据确认不存在 | 类定义、实例枚举、PnP 设备与驱动状态（D17） |
| 能否访问 | 可访问 / 需用户授权 / 被策略禁止 / 被拒绝或不足以判定 | 错误分层（D15）+ 令牌画像（D11）+ provider 元数据（D16） |
| 数据是否可信 | 可信 / 未出结果 / 存疑 / 写后读回不一致 | 合理性校验、回读校验（D3） |

**合成表（必须写成一个 switch 或数据表，不许散在 if 里）**：

| # | 是否存在 | 能否访问 | 数据可信 | 合成状态 |
| --- | --- | --- | --- | --- |
| 1 | 探测未完成（启动或刚唤醒） | — | — | 检测中 |
| 2 | 确认存在 | 可读写 | 可信 | 可用 |
| 3 | 确认存在 | 只能读，不能写 | 可信 | 只读 |
| 4 | 确认存在 | 需用户自行授权才可访问 | — | 需授权 |
| 5 | 确认存在 | 被管理员/组策略禁止，用户不可自解 | — | 策略锁定 |
| 6 | 无证据（可能缺驱动 / 缺数据块） | 不可访问或 0 实例 | — | 未检测到 |
| 7 | 有证据确认硬件/固件没有 | — | — | 不支持 |
| 8 | 确认存在且可访问 | 可访问 | 存疑 | 数据存疑 |
| 9 | 确认存在且可访问 | 可访问 | 写失败 / 写后读回不一致 / 存疑反复出现 | 故障 |

- **读侧判定**回答「有没有、能不能拿到、拿到的是不是真的」；**写侧判定**回答「能不能写、写完对不对」。
- 「只读」（#3）只在读侧通过、写侧不成立时出现；**不能因为写不了就把读值一起藏掉**。
- 合成表里唯一允许自动写的是 #2，且还要满足 D3；其余一律 ❌。

### D2 九态定义（对外唯一口径）

**决策**：对外只有这九个状态；语义、是否允许自动写、推荐 UI 三件事一起定义。**新增/改名状态要改本 ADR。**

| 状态 | 语义 | 允许自动写硬件 | 推荐 UI |
| --- | --- | --- | --- |
| 可用 | 能读能写，数据可信 | ✅ | 正常显示 |
| 检测中 | 启动或刚唤醒，结果未出 | ❌ | 骨架屏/「检测中」，不报问题 |
| 未检测到 | 没发现能力，但不能确定硬件没有（可能缺驱动） | ❌ | 灰显 +「可能缺少驱动」+ 检查步骤 |
| 不支持 | 有证据确认硬件/固件没有该能力 | ❌ | 主界面隐藏，功能清单标「此机型不提供」 |
| 需授权 | 能力存在，用户可自行解决（提权/装服务/加白） | ❌ | 灰显 + 琥珀色锁 + 修复按钮 |
| 策略锁定 | 能力存在，被管理员/组策略禁止，用户无法自解 | ❌ | 灰显 +「由管理员管理」，**不放修复按钮** |
| 只读 | 能读、可信，但不能写 | ❌ | 显示数值，控件灰显 + 原因 |
| 数据存疑 | 有返回值但未过合理性校验 | ❌（依赖它的控制退回安全状态） | 显示 `--` 或最后可信值 + 琥珀色标签，只提示一次 |
| 故障 | 写入失败、写后读回不一致、或数据存疑反复出现 | ❌（恢复默认值） | 红色 + 诊断入口 +「复制诊断信息」 |

三条容易混的边界：

- **不支持 vs 未检测到**：差别是**证据强度**，不是严重程度。前者「隐藏 + 标机型不提供」，
  后者「灰显 + 给检查步骤」。
- **需授权 vs 策略锁定**：差别是**用户能不能自己解决**。后者**不放修复按钮**——放了就是骗人。
- **数据存疑 vs 故障**：差别是**一次还是反复**，以及**有没有写失败 / 回读不一致**。

### D3 自动写入前提：目标能力可用 **且** 依赖输入信号全部可信；写后必须读回

**决策**：

1. **两个前提缺一不可**：
   - 目标能力状态 = `可用`；
   - 该控制**依赖的所有输入信号都可信**。
   例：风扇**可写**，但温度**存疑** → 风扇曲线**照样不能跑**。拿不可信的温度驱动风扇，
   等于用一个假值去改硬件。
2. **写后必须读回校验**：读回不一致 → 进 `故障`（D2 第 9 行）。不许「写成功就当成功」。
3. 读回强度仍按 ADR-0001 D7（`Verified` / `Echo` / `None`）；`Echo` 不算独立验证。
4. **回读失败不许自动重试到成功**：重试纪律见 D20.7（只重试瞬时错误；
   `ACCESS_DENIED` / `INVALID_CLASS` 在同一令牌上下文不重试）。
5. **依赖关系显式声明**：每个控制声明它依赖哪些信号，信号当前是否可信进能力快照，
   不许在写路径里临时判断。

### D4 多原因并存的优先级

**决策**：同一项能力同时命中多个原因时**只取一个**，按此顺序（高 → 低）：

```
故障 > 数据存疑 > 策略锁定 > 需授权 > 未检测到 > 不支持
```

- 取到的原因进快照的 `reason`；其余原因进诊断页明细（D9），**不并列显示在主界面**。
- 顺序的含义：越靠左越「现在就可能出事」（故障 / 假值），越靠右越「这台机器本来就没有」。
  **先解释危险，再解释缺失。**

### D5 视觉与措辞纪律

**决策**：

1. **只有「故障」用红色**，其余八态都不许用红。
2. **「不支持」（A 类）与「受限」（B 类 = 需授权 / 策略锁定）都不用红色，也不用
   「错误 / 失败 / 异常」字眼**：
   - 不支持 = 正常配置，不是故障；
   - 受限 = 一种状态，不是用户的错。
3. 「数据存疑」用琥珀色标签；「需授权」用琥珀色锁；颜色同族但**图标与动作不同**
   （锁 + 修复按钮 vs 标签 + 只提示一次）。
4. 「检测中」**不报问题**：结果出来前不显示任何警告（启动/唤醒瞬间的误报最招骂）。
5. 「只读」要显示数值，控件灰显并给原因；**不许把可读的数据藏掉**。
6. 文案语气见 D10（照抄评审，不许改写）。

### D6 证据门槛：只有确定证据才标「不支持」，不确定就标「未检测到」并给检查步骤

**决策**：

1. **只有拿到确定证据才标「不支持」**：类定义不存在且 PnP 侧确认设备不存在；
   或驱动/provider 明确返回「不支持」。
2. **不确定就标「未检测到」+ 检查步骤**。典型反例：`0x80041010`（INVALID_CLASS）既可能是
   「这台机器真没有」，也可能是**驱动没装 / MOF 未入仓**（D15）。把它判成「不支持」=
   让用户永远不再装驱动。
3. 「未检测到」的检查步骤必须**可执行**，至少覆盖：设备管理器里对应设备是否存在、
   厂商服务是否在跑、驱动版本、是否处于受限环境（Low IL / AppContainer / MSIX / 受限令牌）、
   以及「用户主动触发的提权探测」（D19 第 ④ 步）。
4. 两者缓存策略不同：`不支持` 是「不要再试」的结论 → 长期缓存；`未检测到` 是「还没查清」→ 短 TTL（D20.6）。
5. **判定顺序见 D19**：顺序错就会把权限问题认成「不存在」。

### D7 受限类：需授权可修、策略锁定不可修、B 类影响多项时合并成一条横幅

**决策**：

1. **需授权**：给修复按钮。修复动作限定为**用户自己能做、且走正规路径**的：提权（一次 UAC）、
   装/启动厂商服务、把进程加入允许列表（AppLocker/WDAC/杀软白名单由用户操作）。
   修复后**重新探测**，不许「按了就当好了」。
2. **策略锁定**：显示「由管理员管理」，**不放修复按钮**；给「复制诊断信息」，
   让用户拿去找管理员。
3. **B 类（受限）影响多项时合并成一条横幅**，不在每个控件上挂锁：
   - 横幅写「哪一类原因 + 影响哪些功能 + 一个入口」；
   - 逐项状态仍然进功能清单 / 诊断页，主界面不重复挂锁；
   - 理由：二十个锁图标用户看不出这是**一件事**。

### D8 数据存疑的降级动作（六条，顺序即优先级）

**决策**：一旦判 `数据存疑`，按下面六条执行，**不许只改标签不改行为**：

| # | 动作 | 要求 |
| --- | --- | --- |
| ① | **退回安全方向** | 把风扇还给固件默认 / 切保守预设；**不能停在当前激进设置** |
| ② | **限制手动方向** | 允许降功耗；**拦**提高功耗 / 关保护 |
| ③ | **展示层不显示假值** | 显示 `--` 或最后可信值；曲线**断开**（不画插值） |
| ④ | **恢复要有滞后** | 连续 30–60 秒可信才恢复自动控制，避免反复横跳 |
| ⑤ | **进入降级只提示一次** | 不重复弹；状态在页面上常驻可见 |
| ⑥ | **反复出现升级为「故障」** | 反复出现的数据存疑就是故障（D2 第 9 行） |

- ①是安全底线：**「先停住」比「保持现状」安全**；当前激进设置（高转速锁定 / 关保护）在数据不可信时
  必须退出。
- ③的「曲线断开」比「用最后值延伸」安全：延伸出来的线看着是数据，实际是猜测。

### D9 一个「功能检查」诊断页（逐项状态 + 原因 + 修复）

**决策**：只做一个诊断页，不散在各处。

| 内容 | 要求 |
| --- | --- |
| 逐项状态 | 每项能力：九态 + 一句话原因（D10 文案）+ 修复按钮（仅「需授权」给） |
| 技术细节 | 错误码、接口/类名、方法名、返回值、令牌画像、provider 元数据——**默认折叠** |
| 复制诊断信息 | 一键复制（脱敏后），贴 issue 用 |
| 事件日志 | 运行时**不读**（需要管理员）→ 走「导出诊断包」（D18） |
| 排序 | 有问题的在前：故障 → 数据存疑 → 需授权 → 策略锁定 → 未检测到 → 不支持 → 只读 → 检测中 → 可用 |

- 折叠是必须的：技术细节对普通用户是噪音，对报 bug 的人是全部价值。
- 「复制诊断信息」与 `--probe` 导出同源（ADR-0001 附录 B），必须脱敏（无序列号 / UUID / MAC /
  用户名路径 / 主机名）。

### D10 文案（照抄评审，不许改写语气）

**决策**：下面六条是评审原文，**直接进语言包**，实现时不许「优化」语气：

| 状态 | # | 文案 |
| --- | --- | --- |
| 不支持 | 1 | 「你的机型没有独立的显卡切换开关，显卡由系统自动调度，属于正常配置。」 |
| 不支持 | 2 | 「此机型未提供该功能，其他功能不受影响。」 |
| 需授权 | 1 | 「这一项需要管理员权限才能调节，点「授权」后即可使用。」 |
| 需授权 | 2 | 「这一项暂时被系统设置拦住了，点「查看原因」了解怎么开启。」 |
| 数据存疑 | 1 | 「温度读数暂时不太准，风扇已先交给电脑自带的保护来管理，读数恢复后会自动切回。」 |
| 数据存疑 | 2 | 「传感器数据看起来不对劲，自动调节已暂停，电脑自身的过热保护仍然有效。」 |

补全其余状态的文案时遵守同一语气（**评审只给了上面六条，其余是新增，要按这个语气写、并走评审**）：

- **先说结论 → 再说影响 → 不吓人 → 不甩锅给用户**；
- 不支持类不出现「错误 / 失败 / 异常 / 损坏」；
- 需授权类不出现「拒绝访问」；
- 数据存疑类**必须说明保护仍在**（这是用户最关心的）。

## 4. 决策（探测口径：凭什么判定）

### D11 令牌画像：探测前先采集，与结论一起记录

**决策**：任何探测/判定之前先采集**令牌画像**（每会话一次），并与探测结论一起记录。

| 字段 | 取法 | 用途 |
| --- | --- | --- |
| 完整性级别（IL） | `GetTokenInformation(TokenIntegrityLevel)`，取 SID 最后一个 sub-authority 的 RID（判定见 D12） | 解释「为什么被拒」；诊断第一行 |
| `TokenElevationType` | `GetTokenInformation` | `Default` / `Full` / `Limited`，识别 UAC 降级后的管理员 |
| `TokenElevation` | `GetTokenInformation` | 是否真的提权（不是「在管理员组里」） |
| `IsTokenRestricted` | `GetTokenInformation` | 受限令牌（服务账户 / 受限组） |
| `TokenIsAppContainer` | `GetTokenInformation` | UWP / AppContainer 环境 |
| 包身份 | `GetCurrentPackageFullName` | MSIX 包身份（packaged / full-trust） |
| 组成员 | `CheckTokenMembership` | **deny-only 的管理员组不算成员** |

- **.NET 没有托管 API** 取完整性级别 → 必须 P/Invoke；Win8+ 可用伪句柄 `GetCurrentProcessToken()`，
  不必先 `OpenProcessToken`。
- 画像里还要记**父进程与 exe 文件本身的完整性标签**（低 IL 的常见来源，D13 第 6 条）。
- 画像进快照与导出，但**不据此禁用功能**（D14）。

### D12 完整性级别判定：按区间，不按等值

**决策**：IL 用 RID 的**区间**判定：

| RID 区间 | 判定 |
| --- | --- |
| `< 0x1000` | 不受信任 |
| `0x1000` | 低 |
| `0x2000` | 中（`0x2100` = Medium Plus / UIAccess） |
| `0x3000` | 高 |
| `>= 0x4000` | 系统 / 受保护 |

- **必须按区间**：等值比较 RID 会漏掉 `0x2100`（Medium Plus），把它判成「未知」。
- 这是本文最容易写错的一行代码；单测必须覆盖 `0x1000` / `0x2000` / `0x2100` / `0x3000` /
  `0x4000` / `0x5000`。

### D13 令牌画像的八个坑（全部要进诊断）

**决策**：下面这些不是提醒，是验收项：

| # | 坑 | 后果 | 做法 |
| --- | --- | --- | --- |
| 1 | 用等值比较 RID | 漏 `0x2100`，Medium Plus 被判成未知 | 按区间判（D12） |
| 2 | `WindowsIdentity.Groups` 对部分组过滤不可靠 | 误判「在管理员组里」 | 用 `CheckTokenMembership`；deny-only 组不算成员 |
| 3 | 服务账户「系统级 ≠ 管理员」 | 以为有管理员权限，实际被拒 | 服务 SID 与管理员组分开看；`SERVICE_SID_TYPE_RESTRICTED` 是**受限令牌** |
| 4 | 模拟（impersonation）时看错令牌 | 看的是进程令牌，访问检查用的是别的 | 访问检查看**线程有效令牌** |
| 5 | 受限令牌但 IL = 「中」 | 觉得「中 IL 应该能访问」，实际仍被拒 | 受限令牌即使 IL 是中，访问检查仍可能拒；**以实际调用为准** |
| 6 | 低 IL 的来源判断错 | 只怪「没提权」，漏掉真实原因 | 低 IL 的常见来源是 **exe 文件本身带 Low mandatory label** 或**父进程处于低级别** → 诊断里必须记父进程与 exe 的完整性标签 |
| 7 | 被 UAC 降级的管理员 | 当成「有管理员权限」 | IL = 「中」+ `TokenElevationType = Limited` |
| 8 | 打包/沙箱环境 | 以为只是权限问题 | MSIX full-trust 以「中」运行；UWP / AppContainer 为「低」，且**基本用不了 `root\wmi`** |

### D14 结论纪律：IL 只作诊断依据，不据此禁用功能

**决策**：

1. **不因为令牌画像「看起来不行」就禁用功能**：IL 低不等于一定失败（有的 provider 只读不校验权限），
   反过来 IL 中也不等于一定成功（受限令牌 / 策略 / provider 自查签名）。
2. **最终以实际调用结果为准**：先探测、再判定；画像只写进原因与诊断。
3. 画像可以用来**选择提示方式**（提示提权 vs 解释环境），但不能用来**预先判定能力不存在**。

### D15 错误分层：连接 → 类定义 → 实例枚举

**决策**：错误必须按**发生层**解释；同一个错误码在不同层是不同结论。

| 层 | 错误码 | 含义 | 初判 → 九态 |
| --- | --- | --- | --- |
| 连接层 | `0x80070005` | DCOM / 连接被拒 | 权限或环境 → 需授权 / 未检测到 |
| 连接层 | `0x8004100E` | 命名空间不存在 | 环境不符 → 未检测到（不是「不支持」） |
| 类定义层 | `0x80041010` | INVALID_CLASS：驱动没装 / MOF 未入仓 | 未检测到（**不是**不支持，除非 PnP 确认无硬件） |
| 类定义层 | `0x80041003` | 命名空间 DACL 拒绝 | 需授权 / 策略锁定（看令牌画像） |
| 实例枚举层 | `0x80041003` | 类存在但取数据被拒（provider 或 WMI 数据块 GUID 的安全描述符） | 需授权 / 策略锁定 |
| 实例枚举层 | `0x80041062` | 缺特权 | 需授权（并说明缺什么、怎么补） |
| 实例枚举层 | **0 个实例** | 类存在但无数据块（设备不存在 / 驱动没加载） | 未检测到，并用 PnP 交叉验证（D17） |
| 实例枚举层 | `0x80041013` / `0x8004100C` / `0x80041024` | provider 损坏或不支持 | 按是否可恢复 → 故障 / 未检测到 |

**两个必须防的坑**：

1. **`System.Management` 常在「枚举集合时」才抛错**：只在 `Get()` 外面套 try-catch 会漏异常——
   必须把枚举（`foreach` / `ToList()` / LINQ）一起包住。
2. **连接选项的 Impersonation 必须是 `Impersonate`**：`Identify` / `Anonymous` 也会得到
   ACCESS_DENIED，与「令牌问题」混在一起会得出完全错误的结论。

### D16 provider 元数据：把「为什么被拒」查到 provider 注册里

**决策**：诊断必须能回答「这是权限、是 provider 逻辑，还是根本没人提供」，因此要读 provider 元数据：

| 项 | 内容 | 用途 |
| --- | --- | --- |
| 类限定符 | `provider("WMIProv")` | WDM 驱动经 WMI 桥；此时**访问控制在数据块 GUID 的安全描述符**，不在类 DACL |
| 类限定符 | `guid("{...}")` | 可查 `HKLM\SYSTEM\CurrentControlSet\Control\WMI\Security\{GUID}`（**通常需管理员**）→ 放诊断/导出，**不放运行时** |
| 类限定符 | `Privileges` | 需要哪些特权（与 `0x80041062` 对应） |
| `__InstanceProviderRegistration` | `HostingModel` | `LocalSystemHost` / `NetworkServiceHost` / `Decoupled:Com`，判断 provider 跑在谁的令牌下 |
| `__InstanceProviderRegistration` | `ImpersonationLevel` | **1 = 模拟调用者，令牌决定结果**；**0 = 拒绝来自 provider 自身逻辑**（与权限无关） |
| `__InstanceProviderRegistration` | `CLSID` | 定位 provider DLL → 签名者（排查 provider 自查签名） |

- `ImpersonationLevel = 0` 这行特别重要：它让「被拒」看起来像权限问题，实际是 provider 主动拒绝。

### D17 PnP 交叉验证：类存在 + 0 实例时唯一的真相

**决策**：`类存在 + 0 实例` 必须用 PnP 交叉验证才能定性。

| PnP 结果 | 结论 |
| --- | --- |
| 设备不存在 | 不支持（有证据） |
| 设备存在、驱动未加载 / 服务未启动 | **未检测到**（「可能缺少驱动」+ 驱动检查步骤）；B 材料原文写「不支持」，本文按 D6 收窄，见下方说明 |
| 设备存在、驱动正常、仍 0 实例 | 未检测到 / provider 异常（进诊断，不猜「不支持」） |

- 用 SetupAPI / CfgMgr 查设备存在性、驱动服务状态与问题码。
- **口径收窄（工程 → 产品，必须只写在一处）**：B 材料把「设备不存在」与「驱动未加载」都映射到「不支持」；
  本文按 D6 的证据门槛收窄为**只有「设备不存在」才落「不支持」**，因为驱动可以装，
  把可修复的问题判成「机型没有」正是 §1.2 第 2 类错误。**收窄只发生在 D6/D17/D19 这一步，探测结果不变。**

### D18 事件日志：运行时不读，做成「导出诊断包」

**决策**：事件日志要管理员才能读 → **不放进运行时路径**，只做导出。

| 日志 | 事件 ID | 用途 |
| --- | --- | --- |
| `Microsoft-Windows-WMI-Activity/Operational` | 5858 | 失败详情（`ResultCode` / `ClientProcessId` / `User` / `Operation`） |
| `Microsoft-Windows-WMI-Activity/Operational` | 5857 | provider 加载 |
| System | SCM 7000 / 7026 | 服务启动失败 / 依赖加载失败 |
| `Kernel-PnP/Configuration` | — | 设备与驱动问题 |
| System | DCOM 10016 | DCOM 权限（连接层被拒的旁证） |

- 导出包 = 探测结论 + 令牌画像 + provider 元数据 + 上述日志片段 + 版本信息（全部脱敏）。
- 入口在诊断页（D9），按钮文案「导出诊断包」。

### D19 判定顺序（照抄评审）

**决策**：判定**必须**按这个顺序，不许跳步、不许并行下结论：

```
① 类定义不存在                                  → 不支持
② 类存在 + 0 实例 + PnP 显示设备不存在/驱动未加载 → 不支持
③ 类存在 + ACCESS_DENIED                        → 权限不足（结合令牌画像决定：提示提权 or 解释环境）
④ 拿不准                                        → 用户主动触发的提权探测
```

- 第 ③ 步的「权限不足」在对外九态里**不是一个状态**：用户能自解 → `需授权`；
  管理员/组策略禁止 → `策略锁定`（D7）；判不出来按 `未检测到` + 检查步骤。
- 第 ④ 步的提权探测**必须由用户主动触发**（一次 UAC + 明确告知要做什么），不能后台偷偷提权。
- **与 D6 的衔接（两份材料的口径合并，不新增判定）**：第 ① 步的「类定义不存在」在 D15 里
  同时可能是「驱动没装 / MOF 未入仓」——所以落 `不支持` 之前要先排除 PnP 侧「设备存在但驱动未加载」；
  排除不了就落 `未检测到` 并给检查步骤。

### D20 启动期探测：同步只做画像与缓存，WMI 探测异步 + single-flight + 超时

**决策**：

| # | 要求 | 说明 |
| --- | --- | --- |
| 1 | **同步只做令牌画像 + 读缓存** | 微秒级；启动路径不许等 WMI |
| 2 | **WMI 探测放独立 MTA 后台线程** | 首帧后 / 空闲时执行，不阻塞首帧 |
| 3 | **single-flight** | 同一时刻只允许一个探测，其余请求**等同一个 Task**，不各自再发 |
| 4 | **连接与枚举都设超时**（半同步） | 驱动挂死时把探测放**子进程**并可直接结束 |
| 5 | **缓存键必须含令牌画像** | 否则提权跑出的「支持」会污染普通权限下的判断。完整键：`令牌画像 + 机型 + 驱动版本 + OS build + 应用版本 + 用户 SID` |
| 6 | **按状态区分有效期** | `不支持` 长期；`需授权` 仅在令牌画像相同时复用；瞬时错误短 TTL |
| 7 | **只对瞬时错误重试** | `0x800706BA` / `0x80010108` / `0x80041033` / `0x80041015` / 超时 / decoupled load failure；指数退避 + 抖动 + 总时长上限。`ACCESS_DENIED` 与 `INVALID_CLASS` **在同一令牌上下文不重试** |
| 8 | **等服务就绪用 SCM / `NotifyServiceStatusChange`** | 不要轮询 |
| 9 | **重新探测的触发点** | `CM_Register_Notification`（设备到达/移除）、睡眠恢复、厂商服务重启；**别用 `__InstanceCreationEvent` 轮询** |
| 10 | **探测成功后复用同一个 `ManagementScope`** | 连接断开时重连，并把状态降为「待确认」（对外仍是 `检测中`，不是 `可用`） |
| 11 | **遥测** | 记录探测耗时、各层结果码、令牌画像（脱敏后）——用于定位「只有某些机器 / 某些账户」的问题 |

> #9 的理由：WMI 事件订阅本身就是一层可失败的依赖，而且轮询成本高；用系统通知 + 电源事件 +
> 服务状态变化更可靠。这与 ADR-0002 D2 的「电源/会话事件必须处理」是同一套时机。

### D21 风险与红线

**决策**：

| # | 风险 | 处理 |
| --- | --- | --- |
| 1 | **厂商 provider 不规范**：权限不足时返回空结果或 `WBEM_E_FAILED` | 会被误判成「不支持」→ **按机型维护例外表**（数据文件里，可更新），并把这台机器标成「已知不确定」，而不是标成「不支持」 |
| 2 | 想「顺手」改 WMI GUID 的安全描述符来拿到数据 | **不做**（红线）：改的是系统/厂商的安全边界，影响所有使用者，而且掩盖真实原因 |
| 3 | 想整个应用提权来绕开这些坑 | **不做**：违反 ADR-0002 的 UI 降权。长期方案是**小服务读 WMI + ACL 命名管道给 UI**（ADR-0002 已经是这个形状），不是让 UI 提权 |
| 4 | 例外表变成「万能开关」 | 例外表只允许改**判定提示**（不支持的置信度 / 是否需人工确认），**不允许改探测结果与写权限** |
| 5 | 缓存把错误结论固化 | 缓存键含令牌画像（D20.5）+ 状态分级 TTL（D20.6）+ 版本变化失效（ADR-0001 D6 缓存键） |

## 5. 后果

### 5.1 正面

- **读和写分开**：用户至少还能看见数据（只读），不会因为写不了连读都带走。
- **权限问题与缺失问题分开**：「缺驱动」不再被写成「机型没有」，减少这类永久性误判。
- **九态成了唯一词汇表**：UI 文案、诊断页、日志、issue 模板、机器数据都用同一套状态名。
- **A 类 / B 类不用红色与故障字眼**：用户不被吓到，也不会对「这机器没有」产生错误期待。
- **数据存疑有确定行为**：退回固件默认、限制手动方向、曲线断开——把「不确定」变成确定的安全动作。
- **探测纪律提前堵坑**：single-flight / 超时 / 子进程兜底 / 缓存键含画像，
  把「启动卡死」「提权污染缓存」「重试风暴」这三类事故提前挡在外面。
- **每个「灰」都能回答原因**：错误分层 + provider 元数据 + PnP 交叉验证，让诊断有据可查。

### 5.2 负面 / 成本

- **状态机比 bool 复杂**：9 态 × 多个证据来源，测试面变大（合成规则、优先级、文案、渲染都要测）。
- **新增探测代码量不小**：P/Invoke 令牌 API、区间判定、SetupAPI/CfgMgr、provider 元数据、
  事件日志导出，每一块都是新的失败点。
- **例外表是新的维护面**，而且**写错比不写更糟**（把「不支持」误标成「不确定」会让用户反复折腾）。
- **30–60 秒的恢复滞后会被用户感知成「怎么不马上恢复」**，需要文案解释（D10 的语气规则）。
- **导出诊断包要脱敏**：脱敏不完整就是隐私事故，必须与 `--probe` 共用同一份脱敏实现。
- **排障链条变长**：安全描述符与事件日志要管理员 → 只能导出，不能现场看。

### 5.3 对现有文档与代码的影响

| 对象 | 影响 |
| --- | --- |
| [ADR-0001](0001-machine-provider.md) D6 | 已加注：三态是内部探测口径、九态是产品口径；映射表见本文附录 A |
| [../design/ASUS-ATK-FAMILY.md](../design/ASUS-ATK-FAMILY.md) §10 | 已加注：本机 `0x80041003` 属「需授权」，不是「不支持」 |
| 能力快照（`ICapabilitySet` 等） | 从三态 + `Availability` 扩成九态 + `reason` + 依赖信号可信标记（合成规则 D1、状态语义 D2、映射附录 A） |
| `Performix.App` / `Performix.Overlay` | 九态 → 组件映射；B 类合并横幅（D7）；只有「故障」用红（D5） |
| 设置页 | 新增「功能检查」诊断页（D9）；主界面按「不支持隐藏、其余灰显 + 原因」 |
| `Performix.Host` | 启动期探测、single-flight、子进程兜底、缓存（D20）；令牌画像采集（D11） |

| `tests/` | 合成表驱动测试（9 态）、优先级 6 组组合、IL 区间、错误分层、缓存键含画像、枚举异常捕获 |

### 5.4 不做的后果

- **不做九态、只用三态**：UI 只能「灰着」，用户永远不知道是缺驱动还是没权限——
  这类误判会被当成「这软件不支持」口口相传，事后很难纠正。
- **不做证据门槛**：把权限问题判成「不支持」= 用户永远不会再去修驱动或提权。
- **不做写后读回**：写入静默失败，用户以为生效了——比「不支持」更危险，因为可能停在激进设置上。
- **不做数据存疑的降级动作**：假温度 + 保持激进设置 = 真实过热风险。
- **不做 single-flight / 超时 / 子进程兜底**：驱动挂死时启动卡死、重试风暴、缓存被提权结果污染。

## 6. 备选方案

| # | 方案 | 描述 | 为什么不选 |
| --- | --- | --- | --- |
| A | 继续只用三态（`Declared` / `Probed` / `Verified`） | UI 只有隐藏 / 灰显 / 可用 | 无法解释原因；分不清缺驱动、没权限、管理员禁止；表达不了「读到但不可信」 |
| B | bool + 一堆独立的 `Reason` 枚举 | `IsSupported` + `Reason`，不复用九态 | 原因会被各页面各自翻译，口径必然漂移；D4 的优先级规则无处安放 |
| C | 让 UI 自己看错误码决定显示 | UI 判状态 | UI 不碰 WMI（A6 / ADR-0001 C4），拿不到分层错误码；还要求 UI 懂 provider 元数据 |
| D | 只做「可用 / 不可用」二元 + 详细日志 | 最省事 | 会把「只读」砍掉，用户能看的数值也看不到；「检测中」无法表达 |

| H | 探测同步做在启动路径上 | 少一个线程 | 驱动挂死会卡住启动与首帧，且没有超时无法自愈（D20.1 / 2 / 4） |

## 7. 落地顺序

> 原则：**先状态机与证据，再探测调度，最后 UI 与例外表**。步骤 0–3 不改任何硬件行为。

| 步骤 | 内容 | 退出条件（验收） |
| --- | --- | --- |
| **0. 状态机** | 三维 → 九态合成表、D4 优先级、D3 写闸门（纯逻辑，无硬件） | 表驱动单测覆盖 9 态与优先级 6 组组合；「可用 + 依赖信号不可信」不写；「只读」不隐藏读值 |
| **1. 令牌画像 + IL 区间** | P/Invoke `GetTokenInformation`、区间判定、`CheckTokenMembership`、包身份、父进程与 exe 完整性标签 | IL 区间单测（`0x1000/0x2000/0x2100/0x3000/0x4000/0x5000`）；deny-only 组不算成员；画像进快照与导出 |
| **2. 证据链** | 错误分层（D15）、provider 元数据（D16）、PnP 交叉验证（D17）、判定顺序（D19） | 每个错误码都能落到九态之一并带原因；枚举异常被捕获（不只 `Get()`）；Impersonation 固定 `Impersonate` |
| **3. 探测调度** | MTA 线程 + 首帧后、single-flight、连接/枚举超时、子进程兜底、缓存键含画像、只重试瞬时错误 | 模拟驱动挂死：首帧不卡、探测可结束；并发请求只发一次；提权探测不污染普通权限缓存 |
| **4. UI 九态** | 九态渲染、B 类合并横幅、只有故障红、D10 文案 | 九态逐一可视化验收；不支持 / 受限无红色、无「错误/失败/异常」字眼；检测中不报问题 |
| **5. 诊断页 + 导出** | 「功能检查」页：逐项状态/原因/修复、技术细节折叠、「复制诊断信息」「导出诊断包」 | 技术细节默认折叠；复制内容通过脱敏测试；导出包含 D18 的五类日志片段 |
| **6. 数据存疑降级 + 例外表** | D8 六条动作、30–60 秒滞后、反复升级为故障；按机型例外表 | 注入假温度：退回固件默认、限制手动方向、曲线断开、滞后 30–60 秒、只提示一次、反复→故障；例外表只改提示不改写权限；ASUS 那台 `0x80041003` 落「需授权」 |

**每一步都不做的事**（防止顺序被跳过）：

- 步骤 0–3 期间**不改任何硬件行为**（只建判定，不动写路径）。
- 步骤 2 之前不许把任何「被拒」写进数据文件（否则例外表会掩盖探测 bug）。
- 步骤 4 之前不许在 UI 里直接显示错误码（先把码翻译成九态 + 文案）。
- 步骤 6 之前不许加例外表（例外表是用来兜「厂商不规范」的，不是兜我们自己的 bug）。

## 附录 A：三态（ADR-0001 D6）↔ 九态映射

**正向**：内部三态只能证明「敢不敢写」，不能直接当 UI 状态用。

| 三态（内部） | 能证明什么 | 不能证明什么 | 映射到九态 | 允许自动写 |
| --- | --- | --- | --- | --- |
| `Declared` | 机型数据文件声明「这台机器应该有这个能力」 | 不能证明本机存在（可能缺驱动、可能数据文件写错） | **未检测到 / 不支持**（它是这两个状态的前提，不是结论） | ❌ |
| `Probed` | 非破坏性读取成功：方法存在、签名匹配、读到值、服务在跑 | 不能证明能写；也没有证明值可信 | **只读**（读确定、写未验证）；数据没过校验 → **数据存疑**；被拒 → **需授权 / 策略锁定** | ❌（仅 ADR-0001 D6 的「实验性写入」开关可例外） |
| `Verified` | 写入后回读通过，或维护者在真机验收 | 不保证「现在」仍可用（AC 拔了、服务停了、值存疑） | **可用**（仍要过运行时可用性与 D3 的依赖信号判定） | ✅（且依赖输入全可信） |

**反向**：实现里要能从九态找回内部三态与证据，不许两套状态各存一份。

| 九态（对外） | 内部落点 | 备注 |
| --- | --- | --- |
| 可用 | `Verified` | 同时要求依赖信号全可信（D3） |
| 只读 | `Probed`（读确定、写未验证） | 读值必须显示（D5.5） |
| 数据存疑 | `Probed` + 校验失败标记 | **不许**升到 `Verified`；反复出现按故障处理（D8⑥） |
| 故障 | 本次会话禁止写（证据等级只留诊断用） | 恢复只能靠重新探测（ADR-0001 D6「降级永不升级」） |
| 检测中 | 探测中，无结论（`Declared` 到第一次探测出结果之间也是这里） | 缓存命中「待确认」也归这里（D20.10）；**不许**在这段显示「未检测到 + 可能缺少驱动」，那是 D5.4 说的误报 |
| 需授权 / 策略锁定 | `Probed` 或 `Declared` + 受限原因 | **不改**能力等级，只改能否访问 |
| 未检测到 / 不支持 | `Declared` 或 `Unavailable` + 原因 | 两者差别是证据强度（D6），不是内部等级 |

## 附录 B：九态速查（典型证据 / UI 动作 / 可写）

| 状态 | 最小证据（能落这个状态的最低要求） | UI 动作 | 自动写 |
| --- | --- | --- | --- |
| 可用 | 读成功 + 合理性校验通过 + 写后回读一致 + 依赖信号可信 | 正常显示与操作 | ✅ |
| 检测中 | 探测尚未完成（启动/唤醒/缓存待确认） | 骨架屏，不报问题 | ❌ |
| 未检测到 | 类缺失 / 0 实例 / 被拒但不足以定性，且 PnP 未确认「无此硬件」 | 灰显 +「可能缺少驱动」+ 检查步骤 | ❌ |
| 不支持 | 类定义不存在且 PnP 确认设备不存在，或 provider 明确返回不支持 | 主界面隐藏；功能清单标「此机型不提供」 | ❌ |
| 需授权 | 访问被拒 + 令牌画像显示「用户可自解」（提权 / 装服务 / 加白） | 灰显 + 琥珀色锁 + 修复按钮 | ❌ |
| 策略锁定 | 访问被拒 + 证据指向管理员/组策略，用户不可自解 | 灰显 +「由管理员管理」，**无修复按钮** | ❌ |
| 只读 | 读成功且可信，写路径不存在或未验证 | 显示数值，控件灰显 + 原因 | ❌ |
| 数据存疑 | 有返回值但合理性校验不通过 | `--` 或最后可信值 + 琥珀标签，只提示一次 | ❌（依赖控制退回安全态） |
| 故障 | 写失败 / 写后读回不一致 / 数据存疑反复出现 | 红色 + 诊断入口 +「复制诊断信息」 | ❌（恢复默认值） |

## 附录 C：判定决策树

```
探测请求
 ├─ 缓存命中且未过期？（键 = 令牌画像 + 机型 + 驱动版本 + OS build + 应用版本 + 用户 SID）
 │    └─ 是 → 直接用缓存状态（「不支持」可长期；「需授权」仅在画像相同时复用；瞬时错误短 TTL）
 └─ 否
     ├─ 采集令牌画像（D11 / D12）+ 父进程与 exe 完整性标签
     ├─ 连接 WMI（Impersonation = Impersonate，带超时）
     │    ├─ 0x80070005 / 0x8004100E → 连接层：需授权 或 未检测到（环境不符），绝不判不支持
     ├─ 类定义存在？
     │    ├─ 否（0x80041010）
     │    │    ├─ PnP 有设备但驱动未加载 → 未检测到（给驱动检查步骤）
     │    │    └─ PnP 无设备            → 不支持
     │    └─ 是
     │        └─ 命名空间 DACL 拒（0x80041003，类定义层）→ 需授权 / 策略锁定
     ├─ 枚举实例（异常包住整个集合枚举）
     │    ├─ 0 实例 → PnP 交叉：无设备 → 不支持；驱动未加载 / 驱动正常仍 0 实例 → 未检测到
     │    ├─ 0x80041003（实例层）/ 0x80041062 → 需授权 / 策略锁定（看画像）
     │    ├─ 0x80041013 / 0x8004100C / 0x80041024 → provider 坏/不支持 → 故障 或 未检测到
     ├─ 数据合理性校验
     │    ├─ 不通过 → 数据存疑（执行 D8 六条降级动作）
     │    └─ 通过
     ├─ 写侧（仅当读成功且写入安全等级允许）
     │    ├─ 写 + 回读一致 → 可用（且依赖信号全可信，否则退回只读）
     │    ├─ 通道只读 / 写未验证 → 只读
     │    └─ 写失败 / 回读不一致 → 故障（恢复默认值）
     └─ 仍拿不准 → 用户主动触发的一次提权探测（D19 第 ④ 步）
```

## 附录 D：术语

| 术语 | 含义 |
| --- | --- |
| 九态 | 对外唯一状态集合：可用 / 检测中 / 未检测到 / 不支持 / 需授权 / 策略锁定 / 只读 / 数据存疑 / 故障 |

| provider 元数据 | 类限定符（`provider` / `guid` / `Privileges`）与 `__InstanceProviderRegistration`（`HostingModel` / `ImpersonationLevel` / `CLSID`）（D16） |
| PnP 交叉验证 | 用 SetupAPI / CfgMgr 查设备存在性、驱动服务状态与问题码，给「类存在 + 0 实例」定性（D17） |
| single-flight | 同一时刻只跑一个探测，其余请求共享同一个 Task（D20.3） |
| 半同步 | 连接与枚举都设超时，不无限等；挂死可放弃（D20.4） |
| 数据块 GUID | ACPI-WMI 数据块的 GUID；WDM 驱动的访问控制落在它的安全描述符上（D16） |
| 例外表 | 按机型的已知不确定清单，只改判定提示、不改探测结果与写权限（D21） |
| 降级动作 | 判 `数据存疑` 后必须执行的六条行为（D8） |
